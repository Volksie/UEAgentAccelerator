Measured 20 September 2026 · Unreal Engine 5.8.3 · three real projects · two agents

An agent with a memory stack is right more often, and it gets there faster.

By Louis Larsson-De Wet

We gave the same model the same questions about a large Unreal Engine codebase twice. The first time it had only shell and text search. The second time it also had a memory stack: a routing guide, pre-generated knowledge about every class and Blueprint, an engine-API database and semantic code search. The stack arm answered more questions correctly, got none outright wrong, and used a fraction of the time and tokens.

Even where both agents get there, as on Q014 and Q072, the one without the stack spends about 14 minutes and more than a million tokens rebuilding from raw bytes what the stack already holds. That cost comes back on every question like it.

It is better in every area we measured

The questions fall into eleven kinds of engineering question. With the stack the agent scores higher in all eleven, and it reaches 100% in three of them.

Why a plain search misses what the stack knows

A large Unreal project keeps much of its truth where text search cannot reach. The stack reads those places ahead of time, and serves the result as a query.

Blueprints are binary

Part of any caller list lives in .uasset graphs, which text search skips without warning. The stack walks every Blueprint graph ahead of time, so "who calls this?" includes the Blueprint callers that no C++ tool can see.

The header is not the whole story

UnrealHeaderTool adds flags that are never written in the source. A const BlueprintCallable quietly becomes BlueprintPure. The stack records the effective flags, not only the ones in the header.

Some answers need no code at all

Platform support is resolved from plugin descriptors, using the engine's own rules. That is how the stack answers for a console on a machine with no console SDK installed.

Comments can be wrong

The stack sends the agent to the function body as well as to the comment above it. One benchmark question turns on a header comment that describes behaviour the code does not have. Reading both is how that gets caught.

It stays fast when the questions get hard

Without the stack, time grows with the difficulty of the question. With it, the time barely changes. On 52 harder questions, written to need exactly what the stack holds, the stack took about as long as it did on everyday ones.

What is in the stack

Six layers, each there because the one below it cannot answer a particular kind of question. Any one can fail without sinking the rest.

LayerWhat it isWhat only it can answer
5Design docsWhy a system is built the way it is
4Instruction files with a routing tableWhich layer to ask, so the agent stops grepping out of habit
3Engine API storeWhat a module declares, and where it is available, for targets you never built
2Reflection dump, one file per class and BlueprintEffective flags, replication conditions, Blueprint callers
1Symbol index: clangd, fronted by SerenaDefinitions and references resolved by a real C++ front end
0compile_commands.jsonNothing on its own, but clangd cannot parse Unreal source without it

Layer 1 is built on Serena, by Oraios AI. It’s the semantic code search the agent uses to find definitions and references, driving clangd for the C++ parsing, and the agent called it 132 times across 39 of the questions in this run, so part of this result is theirs. It’s installed separately, from a fork whose patches are meant to go upstream, under Serena’s own licence: GPL-3.0-or-later for the application from v2 onwards, and MIT for its solidlsp component. Thank you to the Serena team.

Where plain search does as well

Questions about where something is defined get answered quickly either way, because the definition is usually one grep away. The stack is still more accurate there (78% to 90%), but it takes a little longer, so on that kind of question the win is accuracy rather than speed. And “why is this built this way” still needs someone to write the design docs: the stack scores well on it only because somebody did.

How this was measured. Both agents used the same model (Claude Opus) and answered the same 191 questions about Unreal Engine 5.8.3 and three projects: Epic’s Lyra sample game, an open-source plugin and a small seed project. The agent without the stack ran in a clean copy of the tree holding only source, config and content, with five built-in tools and nothing we built. The rule behind that is the one part of this that is not a judgement call: the baseline gets nothing we built, and the codebase it is asked about is not altered.

Every answer was graded against a key three times, independently, and the majority grade is used. Before publication, every key that marked the stack’s answer down was re-derived from the source code and the engine database. Eleven turned out to be wrong, the figures here use the corrected keys, and the corrections raised both agents’ scores. 139 of the questions are everyday engineering questions; 52 were written specifically to need what the stack holds, and they are reported separately rather than folded into the headline.

Semantic code search sits on the stack’s side of that line, so these numbers answer “is this worth building”, not “is it worth adding to a codebase that already has good semantic search”. That needs a third arm, which has not been run.
